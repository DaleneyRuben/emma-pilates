# Limit every request per credential and per address

Status: accepted

Login ([ADR-0029](./0029-manage-authentication-in-the-nestjs-backend.md)) and the email-sending endpoints (BE-012, BE-019) have their own throttles, but nothing else stopped one caller from sending the API as many requests as it liked. BE-025 adds one general limit in front of every route.

- **Lanes.** Every request counts against its network address, resolved as [ADR-0087](./0087-trust-forwarded-addresses-only-from-known-hosting-proxies.md) says: **1,200 a minute**. A request that carries a well-formed credential (`Bearer` from the mobile apps, or the admin web's session cookie turned into `AdminSession`) also counts against that credential: **600 a minute**. The request is refused when either lane is full, and a refused request charges neither.
- **Why the credential and not the Account.** A credential belongs to exactly one Authentication Session of one Account, and new sessions come only from the throttled Login, so its lane is the Account's in practice. Reading the Account itself would need a database lookup before any controller runs, on every request; keying on the credential needs none. The counter key is the credential's SHA-256, never the credential.
- **Why authenticated requests also count against the address.** Otherwise anyone could escape the address lane by attaching a made-up bearer value, which only fails later in the controller. The address lane is twice the credential lane because carrier NAT and the studio's Wi-Fi put many people behind one address.
- **Sizes.** Neither app polls; a screen loads a handful of requests, so a person stays far below 100 a minute even at the studio's busiest moment. The admin web's Playwright journeys run with one worker and the Maestro flows at human speed, all from one local address; the backend e2e suite opens a fresh application per spec. A caller who deliberately sends 10 a second for a whole minute is the case being stopped.
- **Answer.** `429` Problem Details with the existing generic code `rate_limit_exceeded` (already what any 429 without its own code answered, and what the apps and admin web already handle) and `Retry-After` in seconds until the window ends. The audit's draft name `rate_limited` was not used, so clients keep one code for a generic 429.
- **Exempt.** `/health/*` (the platform's probes and Better Stack must never be refused) and `/api/v1/email-delivery-events` (Resend's signed webhook can burst after a promotions send).
- **Storage.** Fixed minute windows in the API process's memory, cleared together when the next minute starts, so memory stays bounded by the callers of one minute. Production and staging each run one `api` instance; a second instance would give each caller twice the allowance, which is acceptable until scaling out, when the counters would move to PostgreSQL like the email budgets. A restart forgets the counters.

A PostgreSQL-backed limiter like the email budgets was rejected for now: it would add a write to every request on a 0.2 vCPU service and a 20-connection database. `@nestjs/throttler` was rejected because its guards run after the middleware that resolves the network address and could not see the admin web's credential before the controller guard, and it adds a dependency for about 60 lines of code. Limiting only at Northflank or Cloudflare was rejected because the platform cannot tell credentials apart.
