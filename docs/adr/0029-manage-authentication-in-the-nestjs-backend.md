# Manage authentication in the NestJS backend

Status: accepted

The system-identity module in the NestJS modular monolith will own authentication instead of delegating it to a managed identity provider. It will manage login identifiers, password hashes, authenticated sessions, session revocation, account activation, and password-recovery tokens. Every Account in the first release requires one unique email address as its login identifier across mobile and admin web. A phone number may remain profile or contact data, but it is not used to locate an Account during login. The module will continue to map authentication state to the application-owned Account established in [ADR-0009](./0009-separate-system-account-from-domain-identities.md). This decision supersedes [ADR-0010](./0010-delegate-authentication-to-a-managed-identity-provider.md).

A self-registered Client Account begins with an unverified email address and receives no normal application access. After registration, the client app shows a **Revisa tu correo** state and SendPulse sends a single-use verification link to the submitted address. The link expires after 24 hours. Opening a valid link marks the email as verified; it does not sign the person in automatically, and the person may then return to the app and authenticate normally. Repeated login attempts before verification must not create a normal Authentication Session.

While this self-registered Account is still pending, the same registration flow may correct a mistyped email address from **Revisa tu correo**. The correction must not create an Authentication Session or grant normal access. It immediately invalidates every verification link sent to the old address and sends one new link to the corrected address with a fresh 24-hour lifetime.

An Assistant-created Client Account or Administrator-created Staff Member Account also begins inactive and receives no password from the staff member creating it. SendPulse sends a single-use activation link to the required email address. The link expires after 7 days. A valid activation link proves control of that address, marks it as verified, and lets the recipient create the Account's first password. Staff must never see, copy, or relay that password. Successful activation does not create an Authentication Session; it returns the recipient to the appropriate Login screen to authenticate normally. Resend limits, replacement behavior, and pending-account cleanup will be set with the provisioning and authentication abuse controls.

Before one of these staff-created Accounts is activated, an authorized Assistant may correct the email on a pending Client Account and an Administrator may correct the email on a pending Staff Member Account. The correction preserves the pending Account and its domain identity, immediately invalidates every activation link sent to the old address, and sends one new activation link to the corrected address with a fresh 7-day lifetime. This pending-email correction is not an email-change flow for an activated Account; changing an already verified login address requires a separate, stricter policy.

Password recovery for every Account uses a single-use reset link sent through SendPulse to the Account's required email address. The link expires after 30 minutes. The request response must remain neutral about whether the email identifies an Account. A valid link lets the recipient replace the password; successful completion then applies the Account-wide revocation and replacement-session behavior in [ADR-0030](./0030-use-opaque-server-side-authentication-sessions.md). SMS, WhatsApp, and staff-assisted recovery are not normal recovery channels in the first release. Loss of access to the registered mailbox remains an exceptional-support policy to define separately.

Whenever the system issues a replacement verification, activation, or password-recovery link for the same Account and purpose, it immediately invalidates every older unused link of that purpose. Only the newest link can succeed, and it receives the full lifetime for its purpose starting when it is issued. Cooldowns and request limits remain part of the authentication abuse-control policy.

Repeating the same account-creation request for an email already attached to the corresponding pending Account must reuse that Account and its existing Client or Staff Member identity. It must not create a duplicate identity or overwrite the information already recorded for it. The request invalidates the older unused link and sends one fresh link for the existing pending flow. Public self-registration returns the same neutral **Revisa tu correo** response rather than revealing whether it created or reused an Account. An authorized Assistant or Administrator may instead be told that the matching Account already exists and is pending, and may continue from that pending record. Requests that conflict with the existing identity type or provisioning path require a separate policy; they must not silently repurpose the Account.

Authentication must be implemented with established open-source libraries and platform cryptography rather than custom cryptographic algorithms. Passwords will be stored as adaptively configured Argon2id hashes. Recovery tokens must be cryptographically random, single-use, short-lived, and stored so that a database disclosure does not reveal a usable token. Login and recovery endpoints must resist account enumeration and automated guessing. Session credentials must support expiration and server-side revocation. [ADR-0030](./0030-use-opaque-server-side-authentication-sessions.md) selects the session-credential and client-storage design.

The application remains the source of truth for Accounts, Client and Staff Member links, Staff Roles, Branch assignments, and every authorization decision. Authentication code must not move those domain concepts into credential or session records. Mobile biometrics may unlock a locally stored session credential, but they do not authenticate directly to the backend or replace the backend session.

Operating authentication in the existing backend avoids an additional provider dependency, keeps the native mobile and admin-web flows under project control, and adds no identity-provider subscription to the initial hosting stack. The trade-off is that the project becomes responsible for security updates, abuse controls, credential lifecycle behavior, and authentication tests. Transactional email delivery is provided through the separately selected boundary in [ADR-0031](./0031-use-sendpulse-for-transactional-email.md); SMS and WhatsApp delivery are outside the first-release authentication design.

A managed provider such as Supabase Auth was rejected for the initial release because its operational convenience did not justify its provider dependency, free-tier constraints, and mismatch with some project-specific account-creation flows. A separately self-hosted identity platform such as Logto or Keycloak was rejected because it would add another service to operate while the project only needs its own mobile and admin clients. These options can be reconsidered if authentication maintenance becomes disproportionate or future integrations require standard identity federation.
