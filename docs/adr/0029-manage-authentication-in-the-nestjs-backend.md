# Manage authentication in the NestJS backend

Status: accepted

The system-identity module in the NestJS modular monolith will own authentication instead of delegating it to a managed identity provider. It will manage login identifiers, password hashes, authenticated sessions, session revocation, temporary-password replacement, and password-recovery tokens. It will continue to map authentication state to the application-owned Account established in [ADR-0009](./0009-separate-system-account-from-domain-identities.md). This decision supersedes [ADR-0010](./0010-delegate-authentication-to-a-managed-identity-provider.md).

Authentication must be implemented with established open-source libraries and platform cryptography rather than custom cryptographic algorithms. Passwords will be stored as adaptively configured Argon2id hashes. Recovery tokens must be cryptographically random, single-use, short-lived, and stored so that a database disclosure does not reveal a usable token. Login and recovery endpoints must resist account enumeration and automated guessing. Session credentials must support expiration and server-side revocation. The exact access-token, refresh-token, and client-storage designs remain separate implementation decisions.

The application remains the source of truth for Accounts, Client and Staff Member links, Staff Roles, Branch assignments, and every authorization decision. Authentication code must not move those domain concepts into credential or session records. Mobile biometrics may unlock a locally stored session credential, but they do not authenticate directly to the backend or replace the backend session.

Operating authentication in the existing backend avoids an additional provider dependency, keeps the native mobile and admin-web flows under project control, and adds no identity-provider subscription to the initial hosting stack. The trade-off is that the project becomes responsible for security updates, abuse controls, credential lifecycle behavior, and authentication tests. Email, SMS, or WhatsApp delivery is not provided by this decision; recovery-message delivery and phone-number verification require a separately selected channel or a staff-assisted process.

A managed provider such as Supabase Auth was rejected for the initial release because its operational convenience did not justify its provider dependency, free-tier constraints, and mismatch with some project-specific account-creation flows. A separately self-hosted identity platform such as Logto or Keycloak was rejected because it would add another service to operate while the project only needs its own mobile and admin clients. These options can be reconsidered if authentication maintenance becomes disproportionate or future integrations require standard identity federation.
