# Manage authentication in the NestJS backend

Status: accepted

The system-identity module in the NestJS modular monolith will own authentication instead of delegating it to a managed identity provider. It will manage login identifiers, password hashes, authenticated sessions, session revocation, account activation, and password-recovery tokens. Every Account in the first release requires one unique email address as its login identifier across mobile and admin web. A phone number may remain profile or contact data, but it is not used to locate an Account during login. The module will continue to map authentication state to the application-owned Account established in [ADR-0009](./0009-separate-system-account-from-domain-identities.md). This decision supersedes [ADR-0010](./0010-delegate-authentication-to-a-managed-identity-provider.md).

A self-registered Client Account begins with an unverified email address and receives no normal application access. After registration, the client app shows a **Revisa tu correo** state and SendPulse sends a single-use verification link to the submitted address. The link expires after 24 hours. Opening a valid link marks the email as verified; it does not sign the person in automatically, and the person may then return to the app and authenticate normally. Repeated login attempts before verification must not create a normal Authentication Session.

While this self-registered Account is still pending, the same registration flow may correct a mistyped email address from **Revisa tu correo**. The correction must not create an Authentication Session or grant normal access. It immediately invalidates every verification link sent to the old address and sends one new link to the corrected address with a fresh 24-hour lifetime.

An Assistant-created Client Account or Administrator-created Staff Member Account also begins inactive and receives no password from the staff member creating it. SendPulse sends a single-use activation link to the required email address. The link expires after 7 days. A valid activation link proves control of that address, marks it as verified, and lets the recipient create the Account's first password. Staff must never see, copy, or relay that password. Successful activation does not create an Authentication Session; it returns the recipient to the appropriate Login screen to authenticate normally. Resend limits will be set with the authentication abuse controls.

Before one of these staff-created Accounts is activated, an authorized Assistant may correct the email on a pending Client Account and an Administrator may correct the email on a pending Staff Member Account. The correction preserves the pending Account and its domain identity, immediately invalidates every activation link sent to the old address, and sends one new activation link to the corrected address with a fresh 7-day lifetime. This pending-email correction is not an email-change flow for an activated Account; changing an already verified login address requires a separate, stricter policy.

Password recovery for every Account uses a single-use reset link sent through SendPulse to the Account's required email address. The link expires after 30 minutes. The request response must remain neutral about whether the email identifies an Account. A valid link lets the recipient replace the password; successful completion then applies the Account-wide revocation and replacement-session behavior in [ADR-0030](./0030-use-opaque-server-side-authentication-sessions.md). SMS, WhatsApp, and staff-assisted recovery are not normal recovery channels in the first release. Loss of access to the registered mailbox remains an exceptional-support policy to define separately.

Whenever the system issues a replacement verification, activation, or password-recovery link for the same Account and purpose, it immediately invalidates every older unused link of that purpose. Only the newest link can succeed, and it receives the full lifetime for its purpose starting when it is issued. Cooldowns and request limits remain part of the authentication abuse-control policy.

Requests that could send a verification, activation, or password-recovery email use layered PostgreSQL-backed limits: a cooldown and rolling caps per email address and purpose, a broader budget per first-party client identifier across different addresses, and a looser budget per trusted network address. Authorized staff resends remain subject to the recipient limit as well as broader source limits; there is no unrestricted staff bypass. A request stopped by any layer sends no email and does not issue a token, invalidate the currently valid link, or restart a pending Account's inactivity window.

The recipient-and-purpose lane permits at most one verification or activation email every 60 seconds, five in a rolling hour, and ten in a rolling 24-hour period. Password-recovery email is stricter: at most one every five minutes, three in a rolling hour, and five in a rolling 24-hour period. Only a request that passes every applicable limit and causes the backend to issue a link and enqueue its email consumes these recipient budgets; a suppressed request does not.

Public per-recipient suppression returns the same neutral success response as an eligible or unknown address and does not disclose its recipient-specific `Retry-After`. A client-wide or network-wide limit may return neutral RFC 9457 throttling Problem Details with `Retry-After` because that limit does not depend on whether a particular Account exists. An authenticated staff interface may state that the selected pending Account's resend is limited and show when it can be retried. Exact client-wide and network-wide rolling budgets remain to be defined.

Repeating the same account-creation request for an email already attached to the corresponding pending Account must reuse that Account and its existing Client or Staff Member identity. It must not create a duplicate identity or overwrite the information already recorded for it. The request invalidates the older unused link and sends one fresh link for the existing pending flow. Public self-registration returns the same neutral **Revisa tu correo** response rather than revealing whether it created or reused an Account. An authorized Assistant or Administrator may instead be told that the matching Account already exists and is pending, and may continue from that pending record.

When the same email arrives through a different but compatible Client-creation flow, the existing pending Account, Client, and provisioning path win. A public signup matching an Assistant-created pending Client sends a fresh 7-day activation link; it does not convert the Account to self-registration, accept the submitted password, overwrite Client or Referral data, or authorize the public flow to change the invited email. An Assistant creation request matching a self-registered pending Client keeps the 24-hour verification flow and may send a fresh verification link without overwriting the Client. If the existing identity is incompatible, such as a pending Staff Member encountered by public Client signup or a pending Client encountered during Staff Member creation, the request must not repurpose the Account, rotate its link, or alter its data. The public response remains neutral, while an authorized staff interface may identify the conflict for manual resolution.

A pending Account may be cancelled only before its email is verified or its activation completes. A self-registering Client may cancel through the valid continuation of the registration that created the Account; an Assistant may cancel an Assistant-created pending Client invitation; and an Administrator may cancel an Administrator-created pending Staff Member invitation. Cancellation immediately invalidates every outstanding verification or activation link, removes the Account and its provisional domain identity from active use, and releases the email for a future Account. A later creation request starts fresh rather than reusing the cancelled Account. The system retains only a minimal cancellation audit record identifying who performed the cancellation and when. This flow cannot cancel or disable an activated Account.

The system automatically applies that same cleanup after a pending Account remains inactive for its creation type's window. A self-registered Client Account expires after 7 days without verification, a successful email correction, or a successful verification-link replacement. An Assistant-created Client Account or Administrator-created Staff Member Account expires after 30 days without activation, an authorized staff update, or a successful activation-link replacement. Creation starts the applicable inactivity window, and each listed successful action restarts it. Cleanup invalidates every outstanding link, releases the email, removes the Account and provisional identity from active use, and records the system as actor with the cleanup time. The 7-day and 30-day pending windows are separate from the 24-hour and 7-day lifetimes of individual email links.

Every public Login failure returns the same unauthorized status, RFC 9457 shape, stable `authentication_failed` code, and generic message. This includes an unknown email, an incorrect password, a pending or unverified Account, an inactive invitation without a password, and a disabled Account. None of these outcomes creates an Authentication Session or exposes the Account state through response fields, headers, redirects, or cookies. Neutral recovery and resend actions remain available from Login, while only an authorized staff interface may reveal an Account state that its Role is permitted to manage.

Login performs equivalent Argon2id work before returning a credential failure. An unknown email or Account without a usable password is checked against a fixed dummy hash configured with the same cost parameters as real password hashes; implementation must avoid a quick-exit path and test response-time distributions rather than adding a fixed sleep. Every attempt that does not create an Authentication Session participates consistently in the accepted claimed-email, client, and network throttling rules, so rate-limit side effects do not reveal whether the Account exists or which state it is in. The separately defined throttling response may still return its neutral status and `Retry-After` after the applicable source budget is reached.

Possession of a valid high-entropy verification, activation, or recovery token allows the corresponding link flow to distinguish a current link from one that is expired or already used, because that feedback does not search by email. A random, malformed, or otherwise unrecognized token receives only a generic invalid-link response and cannot reveal an Account identifier or state.

Repeated incorrect login attempts use progressive temporary backoff rather than an Account-wide lockout. The backend evaluates both the claimed email with request-origin signals and broader origin-level activity, so changing one email does not bypass protection and an attacker who knows an email cannot completely lock out its owner. The first five failed attempts in a throttle lane add no enforced delay. The sixth failure starts a 30-second wait, the seventh a 1-minute wait, the eighth a 5-minute wait, and the ninth and every later failure a 15-minute wait. Fifteen minutes is the cap. A request made before the current wait ends returns the throttling response without verifying the password, increasing the failure count, or extending the wait.

Throttled requests return RFC 9457 Problem Details with a stable project-owned code and `Retry-After`, using neutral wording that does not reveal whether the Account exists. A successful Login clears the matching claimed-email-and-origin failure lane immediately. Otherwise, one hour without another failed password verification resets and removes that lane's failure state. Requests rejected during an active wait do not restart the one-hour clock because no password verification occurred. A successful Login does not clear broader origin-level protection.

Broader origin protection combines a random first-party client identifier with the network address. The mobile installation keeps an opaque random identifier generated for this application; the admin web receives an opaque random identifier in a first-party cookie. Neither identifier may derive from hardware attributes, advertising identifiers, contacts, or cross-site tracking. The backend treats the identifier as an untrusted signal that may be cleared or replaced, and therefore enforces both client-wide and looser network-wide budgets. Missing or malformed identifiers fall back to network protection rather than bypassing throttling. Network identity must come from the direct connection or explicitly trusted hosting proxies, never an arbitrary forwarded header supplied by the requester.

Each client identifier may produce at most 20 failed password verifications across all claimed emails in a rolling 15-minute window. Each network address may produce at most 100 across all client identifiers and claimed emails in the same rolling window. Reaching either budget stops further password verification for that source until enough failures leave the window; `Retry-After` reports the time until the next relevant event expires. Requests rejected before password verification do not add an event or extend either window, and a successful Login does not clear these broader budgets. Events leave the throttle state when they age beyond 15 minutes.

The initial implementation keeps shared throttle state in PostgreSQL so every API instance enforces the same limits without adding Redis, CAPTCHA, or another paid service. Throttle keys should use keyed derived values rather than retaining raw client identifiers or network addresses where practical.

Authentication must be implemented with established open-source libraries and platform cryptography rather than custom cryptographic algorithms. Passwords will be stored as adaptively configured Argon2id hashes. Recovery tokens must be cryptographically random, single-use, short-lived, and stored so that a database disclosure does not reveal a usable token. Login and recovery endpoints must resist account enumeration and automated guessing. Session credentials must support expiration and server-side revocation. [ADR-0030](./0030-use-opaque-server-side-authentication-sessions.md) selects the session-credential and client-storage design.

The application remains the source of truth for Accounts, Client and Staff Member links, Staff Roles, Branch assignments, and every authorization decision. Authentication code must not move those domain concepts into credential or session records. Mobile biometrics may unlock a locally stored session credential, but they do not authenticate directly to the backend or replace the backend session.

Operating authentication in the existing backend avoids an additional provider dependency, keeps the native mobile and admin-web flows under project control, and adds no identity-provider subscription to the initial hosting stack. The trade-off is that the project becomes responsible for security updates, abuse controls, credential lifecycle behavior, and authentication tests. Transactional email delivery is provided through the separately selected boundary in [ADR-0031](./0031-use-sendpulse-for-transactional-email.md); SMS and WhatsApp delivery are outside the first-release authentication design.

A managed provider such as Supabase Auth was rejected for the initial release because its operational convenience did not justify its provider dependency, free-tier constraints, and mismatch with some project-specific account-creation flows. A separately self-hosted identity platform such as Logto or Keycloak was rejected because it would add another service to operate while the project only needs its own mobile and admin clients. These options can be reconsidered if authentication maintenance becomes disproportionate or future integrations require standard identity federation.
