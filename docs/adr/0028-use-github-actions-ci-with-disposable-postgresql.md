# Use GitHub Actions CI with disposable PostgreSQL

Status: accepted; the persistent shared development environment is removed by [ADR-0091](./0091-retire-the-shared-development-environment.md), which leaves local, CI, and production environments

GitHub Actions will be the repository's continuous-integration gate. Pull requests and commits intended for production must pass the configured formatting, linting, type-checking, test, architecture, migration, and API-contract checks that apply to their changes. Database-dependent checks provision isolated PostgreSQL through Testcontainers under [ADR-0049](./0049-use-jest-supertest-and-testcontainers-for-backend-tests.md) and build its schema from committed migrations; CI never connects to shared development or production data or credentials.

The environment model consists of developer-local environments, a persistent shared development environment, disposable CI environments, and production. Local development uses containerized PostgreSQL, CI resources exist only for the duration of a workflow, and [ADR-0045](./0045-maintain-a-shared-development-api-and-database.md) isolates Vercel previews behind a shared development API and database. The production API, worker, and database use the providers selected in [ADR-0027](./0027-deploy-the-initial-backend-on-northflank-with-aiven-postgresql.md). A production release must identify and deploy a commit that passed CI. [ADR-0044](./0044-deploy-the-admin-web-to-vercel-through-github-actions.md) makes GitHub Actions the admin web's production deployment path and deploys its validated prebuilt output to Vercel. Production migrations remain an explicit deployment operation rather than an application-startup side effect.

For mobile store releases, [ADR-0038](./0038-use-eas-build-and-submit-for-manual-mobile-releases.md) assigns native builds and store uploads to EAS Build and EAS Submit. Those releases are manually triggered from a commit that passed this GitHub Actions gate; EAS does not replace or duplicate the repository's CI checks.

There will be no additional staging environment beyond the shared development environment. Northflank's two initially selected free services remain reserved for the production API and worker, and the Aiven Free database remains reserved for production data. The shared development database must not be a schema or database inside the production Aiven service because test data, migrations, connection use, and operator mistakes could affect production. Local-only manual validation was rejected because it cannot provide a consistent, shareable preview environment.
