# Retire the shared development environment

Status: accepted

The project keeps three environments: each developer's local environment, disposable CI environments, and production. The shared development environment of [ADR-0045](./0045-maintain-a-shared-development-api-and-database.md) and [ADR-0046](./0046-host-shared-development-on-render-and-neon.md) (the Render Free API and the Neon Free database) is removed, together with the admin-web pull-request previews that called it ([ADR-0047](./0047-create-immediate-protected-vercel-previews-for-pull-requests.md)) and the workflow that migrated it ([ADR-0090](./0090-migrate-the-shared-development-database-from-pull-requests.md)). Vercel deploys only `main`, and the admin web's `/api/v1` proxy routes only the production host to the production API ([ADR-0084](./0084-proxy-admin-api-requests-through-vercel.md)); any other Vercel address gets no API.

The shared environment existed for collaborative preview testing, but the owner is the only person who opens previews. Everything it exercised is covered locally, where the API, the worker, the email capture, the admin web, and both mobile apps run together, or by production, which every merge reaches minutes later through the staged release and its smoke check. What only a deployed host shows was the Vercel side (the routing middleware compiled alone, the rewrites, host-only `__Host-` cookies over HTTPS), and production shows the same after every merge. It never matched production's backend: Render and Neon differ from Northflank and Aiven in proxy hops, TLS settings, and limits, it ran no worker, and it sent no email, so passing there proved little about production. It also cost two workflows, the preview-origin registration, free-tier compute hours, cold starts, and a second set of secrets.

The one gap left is a broken `middleware.ts` or Vercel Function that only fails once Vercel compiles it alone. A unit check in the admin web's suite refuses any local import in those files, so the mistake fails the pull request in CI instead of the production admin web.

This is not the end of pre-production testing. Before real Clients depend on production, a staging environment that mirrors production (the same providers, a worker, staging builds of both apps installed next to the store apps, and a release to staging before production) replaces production as the place to try changes (EXT-017). That decision will get its own ADR; until then, testing on production with synthetic Accounts is acceptable because no real Client relies on it.

Keeping the environment for a future reviewer was rejected because the setup can be rebuilt when one exists, and staging will serve that purpose with production parity. Adding a development worker (EXT-010) was rejected for the same reasons. Keeping previews as frontend-only builds with no API was rejected because a preview that cannot sign in shows nothing the local Vite server does not.
