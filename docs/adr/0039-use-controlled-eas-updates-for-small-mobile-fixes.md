# Use controlled EAS Updates for small mobile fixes

Status: accepted

The mobile application will use EAS Update to deliver small, compatible JavaScript and bundled-asset fixes without requiring users to install a new App Store or Google Play release. Appropriate production updates include JavaScript bug fixes, copy and translation corrections, styling and layout corrections, and replacement assets that do not alter the native application. EAS Update will use Expo's free service allocation while it remains sufficient; exceeding that allocation triggers a new cost and hosting review rather than an automatic paid upgrade.

Production updates are manual releases from an explicit Git commit whose applicable GitHub Actions checks have passed. Before production, the update must be exercised through a preview channel on a build with the same runtime version and representative on-device state. A production update begins as a limited percentage rollout, its available launch and error signals are reviewed, and it is then either expanded or reverted. The exact observation period may reflect the number and activity of installed applications, but an update is never promoted solely because a timer elapsed.

Every production binary and OTA update carries a runtime version, and an update may target only a matching native runtime. Every change to native code, native dependencies, Expo SDK version, permissions, entitlements, or other native application configuration creates a new runtime and requires a new EAS Build and store submission under [ADR-0038](./0038-use-eas-build-and-submit-for-manual-mobile-releases.md). New features or material changes in application behavior also use the store-release path even when technically expressible in JavaScript. EAS Update is not used to bypass platform review. The exact runtime-version derivation policy is selected during implementation from the Expo-supported policies without weakening these constraints.

The release operator must be able to roll back to a known-good published update or the update embedded in the installed binary. Any OTA change to persisted on-device data must remain backward compatible with that rollback; the restricted server-state cache selected in [ADR-0035](./0035-use-an-online-first-read-only-mobile-cache.md) may instead be discarded and rebuilt. An update is not assumed to reach every user immediately: an offline or unopened application continues running its newest available compatible version until it can download and apply another one.

Using OTA delivery for broad feature releases was rejected because it would enlarge the failure and review-policy boundary. Disabling production OTA entirely was rejected because small urgent fixes would then wait for store review and user installation. Self-hosting an Expo-compatible update service was rejected initially because operating its storage, delivery, security, monitoring, and rollback path would cost more engineering effort than the expected usage justifies; it remains an exit path if EAS pricing or constraints become unsuitable.
