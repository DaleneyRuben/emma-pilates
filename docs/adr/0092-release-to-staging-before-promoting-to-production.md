# Release to staging before promoting to production

Status: accepted

The project adds a staging environment that mirrors production, as [ADR-0091](./0091-retire-the-shared-development-environment.md) promised, and changes how a commit reaches production. A merge to `main` releases to staging automatically; production is released only by a person, who promotes a commit that staging has already released and smoke-checked.

Staging runs on the same providers and the same settings as production so that passing there says something about production. It is a second Northflank team, `emma-pilates-staging`, owned by the same login and on the same Developer Sandbox plan, with its own `api` and `worker` services, `migrate` job, and `backup` job, built from the same Dockerfile and released by the same release script. Its database is a separate database, `emma_staging`, with its own role that may connect to nothing else, on the production Aiven PostgreSQL 18 service: Aiven's free plan allows one PostgreSQL service per organization, and opening a second organization or account only to obtain another free service would work around that limit. The shared server keeps Aiven's TLS, CA, version, connection cap, and latency identical, at the price of shared disk, CPU, and connections; staging therefore uses `DATABASE_POOL_MAX=2`, so both environments together stay within the 20 connections with room for migrations and backups. Staging has its own Cloudflare R2 buckets and tokens, its own Better Stack readiness monitor and heartbeats, and reports to the same error-tracking applications tagged with its environment. It holds synthetic data only and is never filled from a copy of production's personal data (the rule [ADR-0045](./0045-maintain-a-shared-development-api-and-database.md) set for development).

The `release staging` workflow runs after `ci` passes on a push to `main`: migrations, API readiness for the commit, the worker, the backup image, then the smoke check, skipping a commit that `main` has already moved past. When the smoke check passes it records the commit status `release/staging` as successful on that commit, and as failed otherwise. The `release production` workflow is started by hand (`workflow_dispatch`). By default it promotes the commit staging's readiness reports, and it refuses any commit without a successful `release/staging` status and any commit that is behind or beside what production already runs, so a promotion can never roll production back. It then runs the same release steps against production and its smoke check, and deploys the admin web from the same commit. A promotion is not refused for being older than `main`: production may lag staging by design.

The admin web follows the same split. A second Vercel project, `emma-pilates-admin-staging`, deploys `main` from Git and proxies `/api/v1` on its own host to the staging API with its own proxy proof ([ADR-0084](./0084-proxy-admin-api-requests-through-vercel.md), [ADR-0087](./0087-trust-forwarded-addresses-only-from-known-hosting-proxies.md)). The production project is disconnected from Git and deployed by the production workflow with the Vercel CLI as prebuilt output of the promoted commit.

Both mobile apps get a `staging` build profile that sets their own application IDs (`com.emmapilates.client.staging`, `com.emmapilates.staff.staging`), a name and icon marked as staging, and the staging API URL, so a staging build installs beside the store app on the same device. Android staging builds are distributed through EAS internal distribution until store testing tracks are opened for them; iOS staging builds wait for the Apple account (gate 9).

GitHub Environment required reviewers were rejected because they need a paid plan on a private repository, which the owner declined; the manual start of the production workflow is the approval. Releasing production on every merge, as before, was rejected because once real Clients use production, new work must be tried somewhere they are not. A second Aiven organization for a separate free staging database was rejected as above. A Northflank PostgreSQL addon for staging was rejected because it differs from Aiven in TLS, certificate authority, connection limits, and network path, which is what staging must catch. Copying production data into staging was rejected for privacy.
