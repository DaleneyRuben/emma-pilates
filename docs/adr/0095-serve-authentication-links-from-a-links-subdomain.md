# Serve authentication links from a links subdomain

Status: accepted

This puts [ADR-0036](./0036-use-verified-https-links-through-a-central-mobile-ingress.md)'s verified HTTPS links on a host. Every authentication email link now points at `https://links.emmapilatesstudio.com` in production and `https://links-staging.emmapilatesstudio.com` in staging, through `AUTHENTICATION_LINK_BASE_URL`. Each host is a Northflank custom domain on that environment's `api` service, and Cloudflare holds a DNS-only `CNAME` for it, so Northflank issues the certificate and the forwarded-address hop count stays the same ([ADR-0087](./0087-trust-forwarded-addresses-only-from-known-hosting-proxies.md)). Custom domains are included in every Northflank plan, so production's free Developer Sandbox can carry it.

The path names the app before the purpose: `/client/authentication/…` for an Account linked to a Client and `/staff/authentication/…` for one linked to a Staff Member. The purposes stay `verify-email`, `activate-account`, `recover-password`, and `confirm-email-change`. Both apps share one host, so Android and iOS need disjoint paths to open the right app without a chooser. Each app's intent filter or associated-domain entry claims only its own prefix, and each app's ingress accepts only its own prefix. The worker reads the Account's link when it renders the message. The prefix is part of the URL, not of the secret, and it grants nothing: the backend still decides what the token is for.

The API serves the verification files itself. `/.well-known/assetlinks.json` lists the store and staging packages with every certificate that signs them: the EAS upload key and Google Play's app-signing key. Listing staging packages on the production host, or the reverse, verifies nothing extra, because each build claims only its own host. `/.well-known/apple-app-site-association` is served as JSON with no app entries until the Apple Developer account exists (gate 9) and its Team ID is known. The iOS associated domains are already in the app configuration.

A browser that reaches a link without the app gets a small Spanish page instead of a 404. The page explains that the link opens in the app and links to the app's Google Play listing. For a Staff Member's activation or recovery link it also offers «Continuar en el navegador», which opens the admin web's existing `/crear-contrasena` page with the same token, because Administrators usually work on a computer. The page never consumes the token. A `GET` that completed an action would let a mail scanner's prefetch use a single-use link before the person does. The page sends `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, and `X-Robots-Tag: noindex`, with a content security policy that allows only its inline styles, so the token does not reach a cache, the Play Store, or a search index.

A separate Cloudflare Worker or Pages site, or the admin web on Vercel, could also have served the host. Both were rejected. They add a deployment that must know each environment's packages and the admin web origin, while the API already has its environment, its admin web origin (`ADMIN_WEB_TRUSTED_ORIGINS`'s first entry, as the bootstrap command uses), and tests. Separate hosts per app were rejected because they double the DNS, certificates, and variables for no gain over a path prefix. A browser page that completes verification or sets a password was deferred: it duplicates the apps' screens for a case the studio does not expect, and the admin web already covers the staff case.

Local development keeps `https://links.emmapilates.test` and the custom schemes, as before.
