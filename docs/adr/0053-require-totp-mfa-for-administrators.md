# Require TOTP MFA for Administrators

Status: accepted

Every Administrator Account must use a standard time-based one-time password (TOTP) authenticator app as a second factor in the initial release. After proving the Account password, an Administrator must also enter the current six-digit code from the enrolled authenticator app before the backend creates a full Administrator Authentication Session. Clients and Staff Members are not required to enroll in MFA initially.

An Administrator who has not enrolled is routed into MFA setup immediately after their first successful password login. This setup state is a restricted challenge rather than an Authentication Session, expires 15 minutes after it is issued, and authorizes only the enrollment flow. If it expires, the Administrator must authenticate with their password again and begin a new setup. The Administrator scans the TOTP setup code, confirms one valid generated code, and is then shown the recovery codes. Only successful enrollment allows the backend to create a full Administrator Authentication Session. Existing Administrators must complete the same gate on their next successful password login after MFA is introduced; there is no password-only grace period.

Enrollment issues ten one-time recovery codes for loss of the authenticator. Each code can satisfy one MFA challenge once and is then consumed. The codes are shown only during enrollment or regeneration, are never sent by email, and are stored only as one-way hashes. The applications warn the Administrator when three codes remain. Regenerating recovery codes immediately invalidates every unused code from the previous set and displays ten new codes once. Recovery codes do not expire on a calendar schedule.

An enrolled Administrator may replace their authenticator from a full Authentication Session only after re-entering the current password and proving the existing factor with either a current TOTP code or one unused recovery code. The replacement secret does not become active until the Administrator confirms a valid code generated from it; abandoning or failing replacement leaves the old factor active. Successful replacement invalidates the previous TOTP secret and every old recovery code, issues ten new recovery codes, revokes every other Authentication Session for the Account, and keeps the session that completed the replacement active.

If an Administrator has neither the authenticator nor a recovery code, the initial release uses email-based emergency recovery instead of another Administrator or a server-side operator. The Administrator must prove the current password and possess a short-lived, single-use recovery link sent to the Account's verified email address. The request and delivery responses remain neutral, and the link follows the token storage, replacement, throttling, and asynchronous email-delivery protections established for authentication links in [ADR-0029](./0029-manage-authentication-in-the-nestjs-backend.md) and [ADR-0031](./0031-use-sendpulse-for-transactional-email.md). Successful recovery invalidates the old TOTP secret and every recovery code, revokes every Authentication Session for the Account, and requires fresh TOTP enrollment after the next successful password login. It does not create an Authentication Session itself.

The TOTP secret is encrypted at rest with key material kept outside PostgreSQL; neither the secret nor a submitted TOTP or recovery code may be logged.

TOTP works with free authenticator apps, follows an interoperable standard, and avoids an SMS, email-code, or identity-provider dependency during normal authentication. Its main trade-offs are weaker phishing resistance than passkeys and the fact that emergency email recovery reduces protection to the Administrator's password and mailbox when every offline recovery code is lost. This simpler recovery path is accepted for the initial low-cost system. Passkeys, WebAuthn, or a stronger organizational recovery ceremony may be added later, but requiring them initially would add cross-platform enrollment, support, and recovery complexity across the admin web and Expo mobile app.
