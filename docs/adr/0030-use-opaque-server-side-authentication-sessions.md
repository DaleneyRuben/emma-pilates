# Use opaque server-side Authentication Sessions

Status: accepted

The system-identity module will authenticate API requests with opaque, server-side **Authentication Sessions**. This term distinguishes a signed-in Account's security session from the Booking & Membership context's scheduled Session. Each successful login creates a separate Authentication Session for that app installation or browser. The backend generates a cryptographically random credential, returns the usable value to the client once, and stores only a one-way digest alongside the Account reference, expiration, and revocation state. The credential carries no Account, Role, Branch, or permission claims; the backend resolves current authorization data after finding the Authentication Session.

The mobile app sends its credential as a bearer token and stores it using the operating system's secure credential storage. Optional Face ID or fingerprint access gates local retrieval of that credential rather than replacing backend authentication. The admin web uses a `Secure`, `HttpOnly` cookie with the SameSite and cross-site-request-forgery controls required by the final deployment origins. Each device or browser has an independent Authentication Session so the backend can revoke one credential without relying on other clients to cooperate.

Every authenticated request performs a server-side lookup, which provides immediate expiration and revocation and keeps authorization changes out of client-carried claims. That database access is acceptable for the system's expected traffic and is simpler to operate safely than access-token and refresh-token rotation. Mobile Authentication Sessions expire after 30 days without meaningful activity and no later than 90 days after login, avoiding frequent sign-in prompts for Clients and Staff Members on their personal devices while ensuring old sessions eventually become unusable. Admin-web Authentication Sessions expire after 30 minutes without meaningful Administrator activity and no later than 12 hours after login because that surface exposes payments, staff management, payroll, and other sensitive operations. Background polling and other automatic requests do not extend either idle timeout. Concurrent-session limits and account-wide revocation events remain separate policy decisions. The model can support a future Administrator impersonation feature through explicit server-side state, but the scope and behavior of impersonation are intentionally deferred.

A short-lived JSON Web Token paired with a rotating refresh credential was rejected for the initial system because it adds two credential lifecycles and leaves issued access tokens usable until they expire unless another revocation mechanism is introduced. A JSON Web Token without server-side session state was rejected because immediate logout, device-specific revocation, and future impersonation would be harder to enforce. The project can reconsider signed access tokens if measured database traffic later justifies the additional lifecycle complexity.
