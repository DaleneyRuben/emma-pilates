# Use SendPulse for transactional email

Status: accepted; the provider is replaced by Resend in [ADR-0094](./0094-use-resend-for-transactional-email.md)

The initial release will send transactional email through SendPulse's managed service. The NestJS backend will depend on a project-owned email-delivery interface, with SendPulse credentials, API types, and delivery behavior confined to an infrastructure adapter. Authentication and other application modules must express the message to send without depending directly on SendPulse, so another provider can replace it without changing domain or application logic.

Authentication use cases will not call SendPulse inside an HTTP request. The Account or token state and a pg-boss email-delivery job are committed in the same PostgreSQL transaction; only after that durable commit does the API return the endpoint's neutral queued or check-your-email response. If the state and job cannot both be committed, neither is retained and the request fails. Provider latency or an outage therefore does not hold open or partially complete the authentication request.

The worker reloads authoritative authentication state before sending and discards a job whose verification, activation, or recovery link has been used, expired, or superseded. A retry reuses the same still-current link rather than issuing a new token. Usable link secrets must not appear as plaintext in pg-boss payloads or logs: link material needed by the worker is encrypted with an application key stored outside PostgreSQL, and queue payloads contain only the minimum routing and encrypted data required for delivery. Delivery remains at-least-once, so duplicate copies of the same still-valid message are possible when provider acceptance is ambiguous; every copy has the same effect and cannot make an invalidated link usable again.

Each SendPulse attempt has a hard ten-second network deadline. An authentication-email job receives at most four attempts in total: the initial attempt and three retries using pg-boss's native bounded exponential backoff ranges of 30–60 seconds, 60–120 seconds, and 120–240 seconds. The complete automatic retry window remains inside approximately ten minutes, and the worker rechecks link validity before every attempt. Network failures, timeouts, provider rate limits, and provider server errors are retryable. Invalid requests, rejected recipient data, and provider authentication or configuration errors fail immediately because repeating the same request cannot repair them. Exhausted and non-retryable jobs enter the failed or dead-letter path with a sanitized failure category for operations; retries never extend the link's lifetime or generate a replacement link.

Public and otherwise unauthenticated authentication flows never expose whether a message is queued, provider-accepted, failed, bounced, or complained; they retain the neutral responses defined by [ADR-0029](./0029-manage-authentication-in-the-nestjs-backend.md). An Assistant may inspect that sanitized delivery state for a pending Client invitation they are authorized to manage, and an Administrator may do the same for a pending Staff Member invitation. `provider-accepted` means only that SendPulse accepted the delivery request, not that the recipient received it. Staff may correct the pending email and request a new link subject to the normal authorization and resend limits, but they cannot inspect raw provider payloads.

A hard bounce or complaint suppresses further authentication email to that normalized address until the address is corrected or an authorized operational process deliberately resolves the suppression. A soft or temporary delivery failure does not create permanent suppression. SendPulse delivery events are normalized and applied idempotently; the callback-authentication mechanism must be verified during provider integration before production. Delivery failure never disables an activated Account, revokes its Authentication Sessions, or changes its authorization. Password-recovery requests remain neutral, and loss of the only usable recovery address follows the separately deferred exceptional-support policy.

SendPulse was selected because its permanent free plan currently provides substantially more transactional-email capacity than the expected needs of the studio, requires no credit card, and includes API and SMTP delivery, authenticated sending domains, and delivery-status webhooks. A managed service also avoids operating email infrastructure, sender reputation, and the AWS SES dependency required by a self-hosted Plunk deployment.

Hosted Plunk was the preferred open-source alternative, but its smaller free allowance and limited operational advantage did not justify choosing it solely for source availability; self-hosting it would add another deployed application while still relying on an external delivery network. Resend was the preferred developer-experience alternative, SMTP2GO the established low-volume alternative, and Brevo the higher-daily-quota alternative, but each offered less free capacity than SendPulse at the time of this decision. Free-tier terms are an external constraint rather than an architectural guarantee and must be checked before production launch.

The studio must own and authenticate a sending domain. Client responses confirm that the request and delivery job were accepted, never that SendPulse delivered the message. Quota exhaustion, operational alerting, delivery-event and encrypted-payload retention, exceptional recovery-address support, and message templates remain separate decisions. Transactional email is not proof that a person received or read a message.
