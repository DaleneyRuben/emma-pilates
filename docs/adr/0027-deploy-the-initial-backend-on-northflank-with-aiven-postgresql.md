# Deploy the initial backend on Northflank with Aiven PostgreSQL

Status: accepted

The initial backend deployment will run the NestJS API and the pg-boss worker as two separate Northflank Sandbox services. Aiven Free will host the single PostgreSQL database selected in [ADR-0011](./0011-use-postgresql-with-schema-per-bounded-context.md). This keeps both long-running application processes and the database available without an initial recurring hosting charge while preserving the modular-monolith and schema-ownership boundaries.

Both services connect to Aiven through its standard TLS PostgreSQL endpoint. The API uses a Prisma-managed pool capped at four connections, and the worker uses a pg-boss pool capped at four connections. These limits leave headroom within Aiven Free's 20-connection limit for deployment migrations, administration, monitoring, and provider operations. The worker retains a session-pinned connection when required by pg-boss and can therefore use PostgreSQL session features such as `LISTEN`/`NOTIFY`; no transaction-mode proxy sits between pg-boss and PostgreSQL.

Schema and pg-boss installation or upgrade migrations run as explicit one-off deployment jobs. Neither the API nor worker performs runtime schema synchronization, consistent with [ADR-0015](./0015-use-prisma-for-postgresql-access.md) and [ADR-0024](./0024-use-pg-boss-for-durable-background-jobs.md). A scheduled Northflank job creates a daily logical `pg_dump` and stores it privately in Cloudflare R2. Aiven's provider-managed disaster-recovery backups do not replace this portable backup, and recovery is considered unverified until a dump has been restored successfully outside the production database.

The free Northflank and Aiven plans are single-provider sandbox resources without a production SLA. That risk is accepted for the initial low-traffic, non-commercial release. Application images, committed migrations, standard PostgreSQL connections, and portable logical backups avoid making either provider an application-level dependency. Storage growth, connection pressure, repeated unavailability, or a material free-plan change triggers a move to a paid Aiven tier or a small PostgreSQL-capable server without changing the domain or API contracts.

Neon Free was rejected because a continuously polling pg-boss worker would keep its compute active and exceed the plan's monthly compute allowance. Supabase Free provides less database storage and no automatic backups, while using Northflank's included database would place the API, worker, and primary data in the same sandbox failure domain. Starting immediately on paid managed PostgreSQL or a virtual server was rejected because the initial workload does not yet justify a recurring infrastructure charge.
