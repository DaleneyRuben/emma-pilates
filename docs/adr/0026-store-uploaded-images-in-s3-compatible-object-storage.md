# Store uploaded images in S3-compatible object storage

Status: accepted

Uploaded image bytes will live in S3-compatible object storage rather than PostgreSQL or the backend filesystem. PostgreSQL, selected in [ADR-0011](./0011-use-postgresql-with-schema-per-bounded-context.md), remains the authoritative store for each object's opaque storage key, purpose, ownership, media type, byte size, checksum, lifecycle state, and relationship to the owning record. Provider URLs are derived at delivery time and are never canonical database identifiers.

Storage access follows the sensitivity of the owning workflow. Transfer-receipt screenshots are private and available only through an authorized Payment workflow. Client profile photos are not anonymously enumerable. Promotion drafts remain private, while published Promotion images may be exposed through a cacheable public delivery path because they are intentionally shown to every client. Separate namespaces and storage policies prevent a public asset rule from exposing a private object.

The backend owns a narrow object-storage interface; domain models and API contracts do not expose provider SDK types, bucket names, or credentials. Uploads use server-generated object keys and are not accepted as application records until their declared type, actual content, size, and ownership have been validated. Because an object-store write and a PostgreSQL transaction cannot commit atomically, the upload workflow has explicit pending and finalized states and reconciles abandoned or orphaned objects.

Clients upload directly through a three-step protocol. First, an authenticated client requests an upload intent for a specific purpose and declares the expected media type, byte size, and checksum; the backend authorizes that purpose, records a pending upload, and returns a short-lived presigned write URL scoped to one server-generated key. Second, the client uploads the bytes directly to the pending storage namespace. Third, the client submits the upload identifier for finalization; the backend verifies the stored object against the intent and inspects its actual content before promoting it to an immutable serving key and allowing it to be attached to a Payment, Promotion, or profile. Pending objects are never served as application assets, and expired intents are removed by a reconciliation job using [ADR-0024](./0024-use-pg-boss-for-durable-background-jobs.md).

Object storage was selected because it keeps database backups small, supports private temporary access and efficient cacheable delivery, and permits backend instances to remain stateless. Direct signed uploads keep image bytes and slow mobile transfers off the NestJS runtime while preserving backend authorization and final validation. Backend-proxied uploads were rejected because they consume application bandwidth and hold API requests open without adding a security property the intent and finalization steps cannot provide. A hybrid of direct and proxied uploads was rejected because it would create two protocols for the same controls.

Storing binary data in PostgreSQL was rejected because image growth would enlarge transactional backups and make cacheable delivery depend on the API and database. A server filesystem was rejected because it couples files to one runtime instance and complicates deployment, recovery, and horizontal scaling.

Cloudflare R2 Standard is the initial production object-storage provider. At the time of selection, its recurring free allowance and zero internet-egress charge fit the project's constrained budget, while its S3-compatible API supports the presigned `PUT` and CORS workflow above without introducing a provider-specific contract. Presigned URLs use R2's S3 API endpoint; any public custom-domain delivery remains a separate concern. The backend adapter keeps the endpoint, credentials, bucket names, and R2-specific configuration outside application and domain code so a later move to another S3-compatible provider does not change API contracts or stored identifiers.

R2 usage alerts are informational rather than a hard spending cap. The application therefore enforces purpose-specific file-size and account quotas before issuing an upload intent, limits signed-URL lifetimes, and removes expired pending objects through reconciliation. Operational setup includes a low budget alert and usage monitoring. Backblaze B2 was the strongest managed alternative, but its download allowance is tied to stored volume; AWS S3's free access is temporary; Vercel Blob has a smaller allowance and would bypass the S3 boundary; and self-hosted Garage would add storage operations while sharing the initial server's failure domain.

This decision does not select the exact signed-URL lifetime, image transformation service, maximum dimensions and sizes, malware-scanning policy, encryption-key strategy, CDN, backup provider, or retention and deletion periods.
