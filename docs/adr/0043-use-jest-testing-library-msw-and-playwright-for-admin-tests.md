# Use Jest, Testing Library, MSW, and Playwright for admin tests

Status: accepted

The admin web application will use Jest for TypeScript unit and component tests, React Testing Library for user-facing React behavior, Mock Service Worker (MSW) for controlled REST responses at the network boundary, and Playwright for a small suite of end-to-end browser journeys. This keeps Jest as the unit-test runner across the mobile and admin applications while adding browser-specific tools appropriate to the static React admin surface.

Jest tests framework-light logic such as Zod form schemas, RFC 9457 mapping, query-key construction, route search validation, and state transitions. React Testing Library exercises components and screens through accessible roles, labels, text, and user interaction rather than component internals or broad snapshot assertions. Tests must not mock the unit under test or duplicate backend business rules in frontend fixtures.

MSW will intercept requests made through the generated OpenAPI client so component tests can exercise loading, success, empty, authorization, validation, and failure states without replacing `fetch`, TanStack Query, or the client module itself. Mock handlers represent transport examples owned by the admin test suite; they are not a second API contract and must remain compatible with the generated client types. MSW may also support local development scenarios, but mocked responses must never be enabled in a production build.

Playwright will verify release-critical workflows through the built application in real Chromium, Firefox, and WebKit browser engines, including responsive narrow-browser behavior where it matters. End-to-end tests should cover only cross-boundary confidence that component tests cannot provide, such as Administrator sign-in and session behavior, Branch-scoped navigation, a representative data-table workflow, a representative mutation, and authorization failure handling. The final environment, fixture provisioning, browser matrix frequency, and which journeys require a real backend remain separate testing-architecture decisions; mocked browser routes must not be presented as full end-to-end coverage.

Vitest with React Testing Library, MSW, and Playwright was considered because Vitest shares Vite's transformation pipeline and would reduce admin-specific configuration. It was rejected in favor of a common Jest unit-test vocabulary and tooling model across mobile and admin web. Vitest with React Testing Library and Cypress was also considered; Cypress offers strong interactive component and end-to-end debugging, but it would overlap with the selected unit/component layer and introduce a different browser-testing model without a project requirement for it.

The project accepts that Jest requires its own TypeScript, JSX, module-resolution, and browser-environment configuration instead of inheriting the Vite pipeline. The exact transformer and DOM implementation will be selected during scaffolding and pinned in repository configuration. Tests and production builds must both pass TypeScript checking so differences between the Jest and Vite pipelines cannot silently redefine application behavior.
